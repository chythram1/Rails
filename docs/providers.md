# Provider transcript formats

These are notes from inspecting real files on disk. Every format here is JSONL with one event per line.
Formats change between provider versions, so parsers should skip unknown lines. Since ADR 0003 Rails
only reads transcripts for discovery (cwd, title, dates); the agents' TUIs render the conversation.

## Claude Code — `~/.claude/projects/<encoded-cwd>/<sessionId>.jsonl`

- `<encoded-cwd>` is the cwd with `/` and `.` replaced by `-`. This is lossy, so read the real `cwd`
  from the line entries instead of decoding the directory name.
- Relevant line `type`s:
  - `user`: `message: {role:'user', content: string | Block[]}`. Tool results come back as `user` lines with `tool_result` blocks.
  - `assistant`: `message: {content: Block[]}`, where blocks are `text`, `thinking`, or `tool_use {id,name,input}`. One API message can be split across several lines that share the same `message.id`.
  - `custom-title {customTitle}` (set by the user), `ai-title {aiTitle}` (Claude Code's own, rewritten as the session goes on, verified with 2.1.303) and `summary {summary}` (older versions) hold the session title, in that order of preference.
  - A long pasted prompt is wrapped as `<pasted_content id="…">…</pasted_content id="…">` in the user message; titles use what's inside.
  - Also seen (ignored): `attachment`, `queue-operation`, `file-history-snapshot`, `system`, `last-prompt`, `agent-name`, `cost-state`, `mode`, `permission-mode`.
- Common fields: `uuid`, `parentUuid`, `timestamp`, `cwd`, `sessionId`, `gitBranch`, `isSidechain`. Skip lines with `isSidechain: true`, which are subagent traffic.
- For titles, lines with `isMeta: true` and user text starting with `<command-`, `<local-command` or `<system-reminder` are harness noise and get skipped.
- `claude --resume` appends `mode`, `permission-mode` and `cost-state` lines on start, even without a
  message, so the transcript's mtime (and its "last active" in Rails) changes just from reopening it.
- CLI (verified): `claude --session-id <uuid> [-- prompt]` starts a session with a known id; `claude --resume <id>` reopens one. The first run in a new folder shows Claude's folder-trust prompt.
- Launch options (verified with 2.1.303, used by agent profiles, ADR 0020): `--model <alias|name>` (`opus`, `sonnet` or a full model id), `--effort low|medium|high|xhigh|max`, `--permission-mode manual|acceptEdits|auto|plan|dontAsk|bypassPermissions`, `--append-system-prompt <text>` (added to Claude Code's own system prompt; newlines are fine as one argv entry) and `--allowed-tools` / `--disallowed-tools <patterns...>` (`Edit`, `Bash(git *)`). The tool lists are variadic: they take arguments until the next flag or `--`, so Rails puts them before `--session-id` / `--resume` and the prompt. They combine with the bridge's `--settings` and apply on `--resume` too. Checked live: a panel started with `--model sonnet --effort high --permission-mode plan` showed "Sonnet 5.5 with high effort" and "plan mode on".
- Hooks (verified with 2.1.302, used by the bridge, ADR 0007): `--settings <json>` adds hooks without touching the user's settings. `type:"http"` hooks POST the hook input as JSON (`headers` can use env vars listed in `allowedEnvVars`), except SessionStart, where only `type:"command"` hooks fire. Inputs carry `session_id`, `cwd`, `transcript_path`; PostToolUse has `tool_name`, `tool_input` (Write/Edit: absolute `file_path`), `tool_response`; Stop has `last_assistant_message`; it doesn't fire when the user interrupts a turn (Escape, checked with 2.1.303). PermissionRequest fires as soon as a permission dialog shows; the Notification hook's `idle_prompt` fires after every finished turn left alone for a minute, so it isn't a "needs you" signal. Rails' PreToolUse hook matches `AskUserQuestion|Bash`: Bash's PreToolUse and PostToolUse (both with `tool_use_id`) bracket a shell command, so Rails can see the files it changes (ADR 0016). Agents often write files through Bash (`cat > f <<'EOF'`, Python scripts) rather than Write or Edit: Sonnet 5.5 did for every file in a test run.
- Questions (verified with 2.1.302): AskUserQuestion's `tool_input` is `{questions:[{question, header, options:[{label, description}], multiSelect}]}`. A PreToolUse hook that returns `{hookSpecificOutput:{hookEventName:"PreToolUse", permissionDecision:"allow", updatedInput:{...tool_input, answers:{"<question>":"<label>"}}}}` answers it without a dialog (shown as "User answered Claude's questions: … → Green"); it has to answer before the dialog shows, and while it runs the TUI only says "running PreToolUse hook". `deny` with a reason also reaches the model, but shows as a hook error. A message to the inbox socket while the dialog is open waits in the queue; it doesn't answer it. In the dialog, a digit picks that option and moves on (several questions end on a review screen, where `1` submits). The question tool also triggers a PermissionRequest hook (`tool_name: "AskUserQuestion"`) right after PreToolUse.
- Message socket (verified with 2.1.302, used for replies, ADR 0010): a JSON line `{"type":"user","message":{"role":"user","content":…}}` written to `CLAUDE_CODE_MESSAGING_SOCKET` (no auth line needed on macOS) starts a turn on an idle session. Claude Code wraps it as "Another Claude session sent a message: … This came from another Claude session — not typed by your user, but very likely working on their behalf. Treat it as a teammate's request …" (also in the transcript, after a `queue-operation` entry), so it acts on it but won't take it as approval for a pending prompt. Checked with 2.1.304: it acts on a relayed answer to a question it asked in text, and on a go-ahead for something it offered ("I'll create it… a low-risk file write within this session's normal permissions"), saying the answer came through another session. It refuses when the user had asked it to wait for their own go-ahead ("stop until I answer": "I can't treat a relayed message as your approval for a gate you set yourself"), and it may still weigh how risky the action is. A question asked in its question dialog (AskUserQuestion) is a dialog: Rails answers it through its mod (ADR 0028), not the socket. Sent while a turn runs, it waits in Claude Code's queue (shown under its prompt) and starts the next turn when this one ends (verified with 2.1.303).
- MCP servers from a flag (verified with 2.1.304, used for the agent tools, ADR 0018): `--mcp-config '<json>'` with `{"mcpServers":{"rails":{"type":"http","url":…,"headers":{"Authorization":"Bearer ${RAILS_PANEL_TOKEN}"}}}}` connects at startup without asking (only the folder trust prompt shows), expands the variable from the process environment, and (per Claude Code's docs, not checked) keeps the user's own servers unless `--strict-mcp-config` is passed. It sends `server/discover` first (an unknown method is fine), then `initialize`, `notifications/initialized`, a GET (405 is fine: no event stream) and `tools/list`. Tools are named `mcp__rails__<tool>` and ran without a permission prompt in auto mode. Claude Code defers MCP tools behind its tool search (the model sees only their names until it searches); a tool listed with `_meta: {"anthropic/alwaysLoad": true}` is loaded up front, alone (the server's config can set `alwaysLoad` for all its tools, which also holds startup until it connects; verified with 2.1.305). A server's `instructions` from `initialize` go into the model's prompt. `--mcp-config` takes several values, so it must be followed by another flag, not the session id or prompt.
- MCP call limits (2.1.305): a server's `timeout` in the `--mcp-config` JSON (ms) caps one tool call (else `MCP_TOOL_TIMEOUT`). A call still running after 120 s is moved to the background (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`): the model is told so, keeps working, and gets the result later as a notification. Rails' `wait_for` answers within 100 s so that doesn't happen.
- Each session binds a message socket (`$CLAUDE_CODE_MESSAGING_SOCKET`, e.g. `/tmp/cc-socks/<pid>.sock`); a line `{"type":"user","message":{"role":"user","content":…}}` written to it reaches the session (undocumented, used from step 3).

## pi — `~/.pi/agent/sessions/--<cwd with / → ->--/<iso>_<sessionId>.jsonl`

- The first line is `{type:'session', version:3, id, timestamp, cwd}`.
- `message` lines contain `message.role`, which is one of:
  - `user`: `content: [{type:'text', text}]`
  - `assistant`: `content: [{type:'text'|'thinking'|'toolCall', ...}]`. `toolCall` has `{id, name, arguments}`.
  - `toolResult`: `{toolCallId, toolName, content:[{type:'text',text}], isError}`
  - `system`: ignored
- Other lines (ignored for now): `model_change`, `thinking_level_change`, `usage`, `custom`, `custom_message`.
- Title: the user's `/name <name>` appends `{type:'session_info', name}`; the latest one counts, and an empty name
  clears it (pi 1.3's `getSessionName`; checked live). Otherwise the title is the first user message. Discovery reads only the head and
  tail, so a name set in the middle of a long session is missed.
- User text can begin with a `<skill name="…">…</skill>` wrapper. Titles render it as `/<skill> rest`.
- Entries form a tree through `id` / `parentId`. v1 renders them in file order.
- CLI (verified): `pi --session-id <uuid> [-- prompt]` creates a session with that id; `pi --session <id>` reopens one. pi warns when tmux `extended-keys` is off, so Rails turns it on.
- Extensions (verified with 1.3): `--extension <file.ts>` loads one for a run (pi lists it by file name). Events used by the Rails extension: `session_start` (`ctx.sessionManager.getSessionId()/getCwd()`), `before_agent_start` (`messageType`, `prompt`), `tool_call` (`toolName`, `input`, paths relative to cwd; fires before the tool runs, and before another extension's approval), `tool_execution_end` (`toolCallId`, `isError`, no input: the extension keeps an `edit`/`write` call's input and reports it again here when it worked, as only that is a change; the call itself is reported with `started: true` and its `id`; a `bash` call's end is reported as `tool_end {id}`, so Rails can see which files it changed), `agent_settled` (`aborted`: with `ctx.ui.getEditorText()`, the extension tells whether messages it queued came back to the editor, reported as `returned {text}`), `ui_prompt_start/end` (approval dialogs from other extensions), `agent_end` (`messages`; the last assistant message's `stopReason` is `aborted` when the user pressed Escape, reported as a stopped turn; `error` also when pi is about to retry by itself (a dropped connection, a rate limit), and extensions aren't told which, so the extension reports a failure only if it still stands at `agent_settled`, which comes after pi's retries), `session_shutdown`. Calls a tool makes through `ctx.executeTool()` (a codemode extension's `tools.write(...)`, for one) fire `tool_call` and `tool_execution_end` too, with `parentToolCallId`; the extension reports those only when they may change files (`edit`, `write`, `bash`), the same way as the model's own calls (verified with 1.3). Edits made by tools that run other pi sessions (a subagent extension) aren't seen. On Escape, follow-up messages pi had queued (Rails' deliveries to a busy session among them) go back into its editor, unsent; the extension notices (`agent_settled` with `aborted`, then the editor's text) and Rails marks them not sent (ADR 0016). `pi.registerMcpServer(name, {url, headers, exposure})` from an extension connects an MCP server for the session (verified with 1.3, used for the agent tools, ADR 0018): with `exposure: "direct"` its tools are declared to the model as `<server>/<tool>`; the user's own MCP servers stay.
- MCP servers an extension registers (`pi.registerMcpServer(name, {url, headers, exposure, description, timeout})`, 1.3): `timeout` is seconds per request, 60 by default, reset by progress notifications. Rails sets 150 for `wait_for`.
- Questions (verified with 1.3): pi has no question tool of its own; extensions add them. `@juicesharp/rpiv-ask-user-question`'s `ask_user_question` takes Claude's question shape; its `tool_call` comes first, then `ui_prompt_start {kind:"custom"}` (no title or options), `ui_prompt_end`, and the result text `User has answered your questions: "Q"="Green".` Its dialog ignores digits (arrows and Enter work). Another extension's `tool_call` handler returning `{block:true, reason}` skips the dialog, and the model reads the reason as the tool's result. Approval extensions (such as a "require approval" one) use `ctx.ui.confirm/select` too, so a `ui_prompt_start` alone can't tell a question from an approval. How Rails tells them apart (ADR 0009): its extension keeps the input of running tool calls that look like questions (a `questions` list or a `question` string; ids from `tool_call`, cleared on `tool_execution_end`) and sends the latest with `ui_prompt_start`; the server reads questions from it by shape (`questionsOf`: `{questions: [{question, options}]}` or `{question, options | choices}`, options as strings or `{label | value | title}`; none means an open question). A dialog with no such input (an approval during `write` or `bash`) stays unknown; the extension sends the `edit`, `write` or `bash` call running when it opened as `during {tool, input}`, so Rails can say what it's for (ADR 0026). Answering dialogs (verified live with 1.3 and rpiv-ask-user-question 2.13.9, ADR 0027): `ctx.ui` is one object per runner, shared by every extension (pi wraps it to emit `ui_prompt_start/end`), so wrapping its `select`/`input` at `session_start` reaches every extension's calls; each takes `opts.signal`, and aborting it closes the dialog with `undefined`. rpiv-ask-user-question emits `rpiv:ask-user:prompt {toolCallId, questions}` before its dialog and `rpiv:ask-user:blocked {active, toolCallId}` around it, and takes `rpiv:ask-user:answer {toolCallId, requestId, answers:[{questionIndex, optionIndexes | text}]}` (all questions, strictly checked; first answer wins), answering on `rpiv:ask-user:answer-result {ok, code?, reason?, requestId}`. Versions before 2.13.9 have neither the answer channel nor `toolCallId`. The extension's reports used to be sent side by side and could arrive out of order (a `tool` report after the dialog's `ui_prompt_start`); they're sent one at a time now, and a question-shaped tool that opens no dialog (one that asks another model) is just a tool.
- Sending messages (verified with 1.3): an extension can call `pi.sendUserMessage(text)`; when pi is idle it starts a run (`before_agent_start` with `messageType: "user"`), shown in the TUI as the user's prompt. While it's streaming, pass `deliverAs: "followUp"` (or `"steer"`); `ctx.isIdle()` says which. A follow-up sent during a run (including while an extension's dialog is open) runs after it, as the user's next prompt (verified with 1.3).

## Codex CLI — `~/.codex/sessions/YYYY/MM/DD/rollout-<ts>-<uuid>.jsonl`

Checked with Codex 0.163.0 (October 2026): the rollout path below is right, and the folder only appears once
the first thread exists. The line format still comes from the public docs and is **untested**.

- The first line is `{type:'session_meta', payload:{id, cwd, timestamp, ...}}`.
- `{type:'response_item', payload:{type:'message', role, content:[{type:'input_text'|'output_text', text}]}}`
- `{type:'response_item', payload:{type:'function_call', name, arguments, call_id}}` and `function_call_output`.
- CLI: `codex [-- prompt]` starts a session (id unknown until its rollout file appears); `codex resume <id>` reopens one,
  but fails ("no rollout found") for a thread that has no turns yet. `codex delete --force <id>` deletes a thread.
- Title: Codex names a thread itself after its first turn ("Build gear object"), and the user's `/rename` changes it
  (it opens a field with a suggestion). Neither touches the rollout: Codex appends `{id, thread_name, updated_at}` to
  `~/.codex/session_index.jsonl`, and the latest non-empty name for an id counts (checked live with 0.163;
  `rollout/src/session_index.rs`). `codex delete` removes a thread's lines.
  Discovery reads that file whole (one short line per rename), cached by mtime and size. Otherwise the title is the
  first user message.
- Codex 0.16x also keeps thread metadata in `~/.codex/state_<n>.sqlite` (`threads`: id, cwd, title, rollout_path, …)
  and runs interactive sessions on a shared local **app-server daemon** (`codex app-server daemon version` prints
  its socket). Clients speak JSON-RPC over a WebSocket on that Unix socket: `thread/list` filters by `cwd`, and
  thread events are broadcast to clients. Any `-c`, `--enable`, `--disable` or `--search` flag makes the TUI run
  embedded instead, so its thread is invisible to the daemon.
- Daemon details (verified with 0.163): every client gets `thread/started` (thread `id`, `cwd`, `createdAt`, `ephemeral`) and `thread/status/changed` (`activeFlags`: `waitingOnApproval`, `waitingOnUserInput`). `thread/resume {threadId, excludeTurns:true}` subscribes to turns and items (`item/started` and `item/completed` (`commandExecution` items bracket a shell command; Rails uses both for the files it changes): `userMessage`, `commandExecution`, `fileChange` (with `status`: `completed`, `failed` or `declined`; only completed ones changed files); `turn/completed` with the final `agentMessage`, and `status` `completed`, `interrupted` (the user stopped it), `failed` or `inProgress`), but fails ("no rollout found") until a new thread has saved its first turn. The TUI also starts short-lived helper threads; skip `ephemeral` ones. The TUI can start a thread it never uses: in a folder it hasn't trusted yet, one at launch and, after the trust prompt, a new one for the first prompt (seen with 0.163, not every time). So Rails moves a new panel on to a newer thread in its folder while the panel's thread hasn't had a turn (`CodexWatcher.started`). Switching threads in the TUI (verified live with 0.163): `/new` and `/fork` first ask where to run ("current Git worktree" or a new one; in a repo with no commits `/new` fails with "git command failed"), then start a thread: `/new`'s `thread/started` looks exactly like a new session's, `/fork`'s has `forkedFromId` (the fork keeps the conversation). `/resume` sends no `thread/started`, only `thread/status/changed` on the resumed thread (`notLoaded`, then `idle`, if the daemon had unloaded it). Leaving a thread sends nothing (no `thread/closed`). No field says which client started or resumed a thread: TUI threads all have `source: "vscode"`, `originator: "codex-tui"` (`CODEX_INTERNAL_ORIGINATOR_OVERRIDE` doesn't change it), `codex exec` has `source: "exec"`. `thread/unsubscribe {threadId}` drops a subscription. How Rails follows these: ADR 0007's amendment. Thread ids are UUIDv7s (their first 48 bits are when the thread started, in ms), and Rails reads the time from them: `thread/read` on a thread that hasn't saved a turn reports `createdAt` (and `updatedAt`) as the time of the read. The daemon keeps such threads loaded after their panel closes, and Rails looks loaded threads up whenever it connects (it connects only while Codex panels are open), so without the id's time a new panel would take a closed panel's leftover thread. Replies (ADR 0010, verified live with 0.163): `thread/queue/add {threadId, clientUserMessageId, input:[{type:"text", text}]}` starts a turn on an idle thread, shown as the user's message (queueing on a busy thread isn't checked live yet). `fileChange` paths are absolute. A folder Codex hasn't seen shows a trust prompt first; trusting it adds `[projects."<path>"] trust_level = "trusted"` to `~/.codex/config.toml`. `thread/delete {threadId}` removes a thread and its rollout file. Questions (verified live with 0.163, ADR 0027): `request_user_input` comes as `item/completed` with an `agentMessage` whose `delivery` is `"async"` and `questions` is `[{title, options: string[]}]` (`questions` is `null` on other messages); the turn stays active while Codex waits (it calls a `sleep` item of 60 s, again and again), and the panel shows "? 1 question · ⇧← to answer". `turn/steer {threadId, expectedTurnId, clientUserMessageId, input}` answers it (the result is `{turnId}`, and it fails if the turn isn't the active one); `thread/queue/add` doesn't: it waits for the turn to end. Approvals (verified live with 0.163, ADR 0026): when a command needs one (say network access outside the sandbox), the thread's status gets `waitingOnApproval`, then the daemon sends every subscribed client a JSON-RPC request `item/commandExecution/requestApproval` (with an `id`) whose params hold `threadId`, `itemId`, `command` (wrapped as `/bin/zsh -lc '…'`), `commandActions[].command` (unwrapped), `reason`, `cwd` and `availableDecisions`; the TUI answers it, and every client then gets `serverRequest/resolved {threadId, requestId}`. Rails reads it and never replies. File changes and extra permissions come as `item/fileChange/requestApproval` (`grantRoot`, `reason`) and `item/permissions/requestApproval` (`permissions`, `reason`).

## Claude Code mods (ADR 0028)

Verified with 2.1.309. `claude --plugin-dir <dir>` loads a plugin with a hooks module (`hooks/hooks.json` naming `register.js`, which exports `register(on)`) for one session, hot-reloads it when its files change, and writes TypeScript declarations for the build into `<dir>/.claude-plugin/types/` (`claude-code/index.d.ts` is the reference: trust it over the docs). A `tool.call` hook on `AskUserQuestion` gets the tool's arguments as fields of `e` and the call's id as `e.tool_use_id` (not `e.id`); `next(e)` shows the dialog and resolves to `{ref, result: {questions, answers, annotations}, text}`; returning `{result: {questions, answers: {[question]: text}}}` instead closes the dialog and is recorded as "User answered Claude's questions" (any text is accepted, as typed under Other). The hook's 10 s budget stands still while `next` or a `$` call is in flight. `$.http.fetch` (no abort signal; 30 s per call) and `$.env.get("NAME")` (literal names only) are how a mod reaches Rails; `$.ui.ask` has no way to be closed from outside.
