# Domain glossary

The shared vocabulary for Rails. Use these terms in code, UI copy, and docs. If you introduce a new
domain concept, add it here first.

| Term | Meaning | Not to be confused with |
| --- | --- | --- |
| **Project** | A local directory attached to Rails by absolute path. All sessions belong to exactly one project. Stored in our DB. Removing a project only *detaches* it: transcripts stay on disk, and attaching the same path again brings its sessions back. Removal is refused while the project has open panels. | A git repository. A project _may_ be a git repo, but doesn't have to be. |
| **Provider** | A coding-agent product Rails can read and/or drive: `claude` (Claude Code), `codex` (OpenAI Codex CLI), `pi`. Identified by a `ProviderId`. | The LLM vendor or model. Pi can talk to Anthropic models, but its provider here is still `pi`. |
| **Session** | One agent conversation, identified by `(provider, providerSessionId)`. The provider's on-disk transcript is the source of truth for its history. The UI may call these "chats". | A browser connection or login session. |
| **Transcript** | The provider-owned file on disk that records a session (for example `~/.claude/projects/<enc>/<id>.jsonl`). Rails reads transcripts and never writes them. | Our own DB rows, which are only an index. |
| **Discovery** | Scanning provider transcript stores to find sessions whose `cwd` is inside a project's directory. This is read-only. | Attaching a project, which is always an explicit user action. |
| **Adapter** | The server-side discovery code for one provider (`providers/<id>.ts`: `scan`). It finds sessions and their titles. Running an agent is not an adapter's job; panels run the provider's own CLI. | — |
| **Workspace** | A project's arrangement of panels: split panes with tabs. One per project; the layout is saved on the server so every device opens the same arrangement. | The Rails app as a whole. |
| **Panel** | One terminal tab in a workspace, running a provider's native TUI (`claude`, `codex`, `pi`) or a plain `shell` in the project folder. Its process runs in its own tmux session, so it survives browser disconnects and server restarts, and every connected client sees and types into the same terminal. Closing a panel stops its process, and a panel closes itself when its process exits (`exit`, `/exit`, a crash). | A session. A panel may show a session (agents) or none (shells). |
| **Bridge** | How agents in Rails panels report what they do (ADR 0007): Claude Code hooks, the Rails pi extension, Codex's app-server daemon. Each panel has its own bridge token. | The access token, which panels never get. |
| **Board** | Per project, what each open session is doing (status, what it was asked, files it changed, its last reply), folded from what the bridge received. What a Sprocket reads instead of transcripts. | A transcript. |
| **Needs attention** | A panel whose agent waits for the user (a permission, a question, a form) or whose turn failed. Its session dot and tab marker are red. | Busy (yellow), which is only about output. |
| **Busy** | A panel whose program keeps printing output, as an agent does while it thinks or replies. The sidebar shows its session's dot yellow instead of green. | A panel that is merely open (green). |
| **Sprocket** | One of the user's always-on agents (ADR 0005): a shape (one of 8), a colour, one accessory or none, a name, and a chat. It replies on a model the user sets up and can be attached to one project (ADR 0006). Sprockets replace the earlier "home agent" idea. | A provider or a panel. |
| **Coordinator** | The one Sprocket per project that Rails wakes when a session there waits for the user (ADR 0009), set with a switch in its settings. Later the only one that may message sessions. | Any Sprocket attached to the project. |
| **Watch** | How Rails follows a project's sessions for its Coordinator: code that decides when a wait (a question in a dialog, or a turn that ends with one) is worth waking it for. | A Sprocket reading the board when asked. |
| **Event** | A message from Rails in a Coordinator's chat: which session waits for the user and what it asked. The Coordinator's reply follows, or a "nothing needed" mark. | A SessionEvent, what the bridge records. |
| **Rule** | One of a Coordinator's standing rules (ADR 0011): a plain sentence from the user on how to answer sessions ("If it asks whether to continue with its plan, say yes."). Each suggestion says which rule it followed. | Its description, which covers everything it does. |
| **Suggestion** | What a Coordinator drafts for a session (ADR 0010), shown under its message: an answer to a question the session asked (it expires when the session moves on; a dialog's answer is picked in the panel), or a message the user asked it to pass on (a busy session gets it after its current turn). The user sends it, edited or not, or dismisses it. | A message a Sprocket sends on its own (not yet). |
| **Look** | What a Sprocket looks like: its shape (`character` in code), colour and accessory. | |
| **Run** | One bounded attempt by a Sprocket to reply: it starts when the user writes (or an event wakes a Coordinator) and ends with a reply or a notice. | A panel's process. |
| **Description** | What the user wants from a Sprocket, in a few sentences (at most 500 characters): its standing instructions, like a small AGENTS.md. It follows it in every reply and keeps it across projects. | Its core memory, which the Sprocket writes itself. |
| **Capability** | Something a Sprocket can do (read the board, a session's conversation, git, a file; remember), as a server function with a schema. The Sprocket's model reaches capabilities through codemode: it writes a script that calls them (ADR 0008). | A Provider's own tools inside a panel. |
| **Core memory** | A Sprocket's own short note (at most 1,500 characters) about its user, kept with its `remember` tool. Internal: not shown in the UI. It stays with the Sprocket when it moves to another project. | Its chat, which belongs to one project. |
| **Decision model** | A fast model that answers typed questions (yes/no, one of a few options) instead of writing text: a classifier such as TypeSafe's Jev (ADR 0012). It judges in shadow: Rails logs its answers next to its own decisions. Once picked, it may also wake the Coordinator where it's sure and Rails' rules weren't (ADR 0013); `RAILS_DECISIONS=shadow` keeps it to judging. | A Sprocket's model, which writes its replies. |
| **Recent decisions** | The decision model's judgments, next to what Rails decided in code and where a wake led (Settings → Models, collapsed). Called the shadow log when the model only judges. | A Sprocket's run log. |
| **Model provider** | A service Sprockets run on (OpenAI, Anthropic, OpenRouter, …), set up with an API key or a sign-in in Settings → Providers. | A Provider (Claude Code, Codex, pi). |
| **Resume** | Opening an existing session in a panel with the provider's own command: `claude --resume <id>`, `pi --session <id>`, `codex resume <id>`. Opening a session that already has a panel focuses that panel instead. | — |
| **Client** | A browser tab or device connected to the server over WebSocket. There can be many at once, each attached to panels as its own tmux client. | A user. v1 has exactly one user. |
| **Access token** | A shared secret that gates the whole server. v1 is single-user. "Sign out everywhere" (Settings → Account) replaces it. | — |
| **Profile** | The name and avatar (one of 8) at the foot of the sidebar, set in Settings → Account and shared by every device. The name is the computer Rails runs on until the user changes it. | Agent profiles in Customize (not built yet). |
| **Settings** | The modal for the app itself (this server, model providers, the account), opened from the account row at the foot of the sidebar. Its search finds single settings by name or synonym. | Customize, which is for agent profiles, prompts and tools (not built yet). |
| **Automation** _(future)_ | A saved prompt plus project plus schedule or trigger that starts sessions without a human. | — |
| **Harness** _(future)_ | Rails' own agent loop, as opposed to driving a third-party provider. | — |
